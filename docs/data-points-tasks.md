# C 同学任务：数据、积分、奖励兑换与测试

状态基线：2026-09-25。现有账号、任务、成果表及学习流程已由 B 完成；积分和兑换尚未实现。本文包含的是**待开发方案**，不是已有接口承诺。

## 1. 负责范围

- 在现有 SQLite + SQLModel 架构中增加积分账户/流水与奖励兑换。
- 将教师审核通过与积分发放接入同一个事务。
- 准备奖励演示数据、回归测试和可重复运行的测试套件。
- 与 B 协调数据库结构变更，与 A 确认新接口契约。

不要重建登录系统、另建第二套用户表、从前端传入任意学生编号发积分，或把所有积分状态只存在浏览器里。

## 2. 第一优先级：审核通过后发积分

业务规则先与团队确认：

1. 只有教师审核通过的成果产生积分；提交、退回、重交不发积分。
2. 基础版可采用每次通过固定奖励，具体分值由团队确认后在后端统一配置。
3. 一条成果最多获得一次审核奖励；重复请求不能重复发放。
4. 积分金额由服务器决定，前端不能自行指定奖励金额。
5. 已有的 approved 记录不自动补发。若需补发，单独确认范围并使用可审计、幂等的补发脚本。

### 必须遵守的事务边界

当前 `backend/app/services/learning.py` 的 `review_submission` 执行条件更新后，在函数内部调用 `session.commit()`。

与 B 一起调整为：条件更新成功 → 当决定为 approved 时写入积分流水并更新余额 → 统一提交事务。失败时整个事务回滚，不能出现“审核成功但积分失败”。

积分服务接收同一个 `Session`，内部不要另开连接或提前 `commit()`；允许按需要 `flush()`，由上层业务统一提交。数据库唯一约束负责防重复，不能只依赖“先查有没有，再插入”。积分按获益学生计入，不是按正在操作的教师计入。

建议为审核奖励设置唯一的来源键，如固定 `source_type` 与 `source_id=submission.id` 的组合。同一来源不能重复计分。最终表结构、唯一约束和失败处理要与 B 确认。

## 3. 第二优先级：积分查询与奖励兑换

推荐最小数据设计，字段命名可在实现前共同确认：

| 数据对象 | 需要表达的内容 | 关键约束 |
| --- | --- | --- |
| 积分账户 | 用户编号、当前余额 | 一名用户一个账户；余额不得小于 0 |
| 积分流水 | 用户编号、增减值、原因、业务来源、创建时间 | 流水可追溯；业务来源防重复；不允许客户端随意记账 |
| 奖励 | 名称、说明、积分价格、库存、是否可兑换 | 积分价格为正数；库存不得为负 |
| 兑换记录 | 用户、奖励、实际扣分、状态、请求幂等键、创建时间 | 保留兑换时价格；同一用户的同一请求不能重复扣费 |

若采用其他余额计算方案，需解释并测试并发安全。不要保存余额却不留流水，也不要把物品当前价格当成历史兑换金额。

兑换必须在一个事务里完成：验证奖励有效 → 检查并扣减足够的余额与库存 → 写入扣分流水和兑换记录 → 提交。余额/库存检查与扣减应采用条件更新或等效的事务保护，不是仅在 Python 中比较一次。

重复兑换请求应使用幂等键识别；同一键重试返回原结果，不再扣费。同一键搭配不同请求内容应拒绝，避免错误复用。

可先选择能真实交付的数字资料或明确标注的演示奖励。AI Token、运动场地等只是早期构想；没有供应方、额度、成本和履约方案时，不要宣称已经能够兑换真实服务。

## 4. 拟议接口：需确认后实现

以下接口**当前均不可调用**。先和 A/B 确认，再实现并更新后端接口文档。

| 建议方法与路径 | 用途 | 建议权限 |
| --- | --- | --- |
| `GET /api/points/me` | 当前学生积分余额 | 学生本人 |
| `GET /api/points/transactions` | 当前学生积分流水，支持分页 | 学生本人 |

基础版可以通过初始化脚本管理演示奖励，暂不必开发完整管理后台。禁止提供“任意用户任意加分”的公开接口。

## 6. 数据库迁移与可重复运行

- 当前使用 `create_all()` 创建缺少的表，不会自动替已有表增加/修改列和约束。
- 新增独立积分表可以通过明确的建表步骤创建；修改现有表时需准备迁移方案和验证步骤。
- 迁移前停止写入并做好可恢复备份；SQLite 使用日志模式时要考虑数据库及相关日志文件的一致性，不盲目复制正在写入的单个文件。
- 不删除队友的 `data/app.db`，不用“删库重建”代替迁移。
- SQLite 外键约束是否启用需要明确验证；声明 `foreign_key` 不等于已经对每个连接启用了数据库级检查。
- 记录统一的时间格式，建议使用 UTC，并向前端明确时区转换规则。
- 统一并记录可复现的依赖版本；测试依赖要在开发依赖说明中列出。
